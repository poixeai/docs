Poixe implements a **Cache Affinity Routing** mechanism to increase the cache hit rate of upstream APIs and thereby reduce actual billing costs.

## Background

Mainstream model providers (OpenAI, Anthropic, etc.) all offer **Prompt Caching**: when consecutive requests share the same prefix, or when caching is explicitly marked, the upstream reuses previously cached computation results and bills the cache-hit portion at a discount.

But caching has a key constraint: **a cache is bound to a specific channel (API Key / account) and cannot be shared across channels.**

In an aggregation gateway scenario, Poixe's backend connects to multiple upstream channels, and requests are allocated by default by a weighted load balancing module. This means consecutive requests from the same user may be distributed to different channels, causing the upstream cache to be invalidated frequently.

Cache affinity routing exists to solve this problem.

## How it works

<Steps>
  <Step title="First request">
    A user requests a model (such as `claude-opus-4-6`). The system assigns it to an upstream channel using the normal weighting logic. After the request succeeds, the system records the binding: **user + model → channel**.
  </Step>
  <Step title="Subsequent requests">
    While the binding is valid, that user's subsequent requests for the same model are **preferentially routed to the same channel**, so the upstream cache can be reused.
  </Step>
  <Step title="Binding expires">
    Once the binding expires, the system falls back to the default weighted load balancing logic and reassigns a channel.
  </Step>
</Steps>

## Binding expiration conditions

Bindings are short-lived and fragile. They are automatically released when any of the following conditions is met:

| Condition | Description |
|------|------|
| **TTL expiry** | A binding is forcibly invalidated **5 minutes** after creation, with no renewal |
| **Request count limit** | A single binding carries at most **100** requests and is released automatically after that |
| **Channel error** | If the bound channel returns any error (whether or not it is caused by the user's request body), the binding is released immediately |
| **Insufficient channel rate** | After a request completes, if the channel's TPM / RPM is too low, the system declines to establish an affinity, prioritizing request health over caching benefits |

<Callout type="info" icon="info-circle">
  An expired binding does not cause requests to fail. The system immediately falls back to weighted load balancing and handles the request normally.
</Callout>

<Callout type="warning" icon="exclamation-triangle">
    **Why proactively decline affinity when the rate is insufficient?** If affinity is established on a channel whose rate is already running short, the next request can easily trigger a rate limit and enter the retry phase, significantly increasing latency or even causing the request to fail. Following the principle of **request health over cache cost**, the system proactively gives up affinity in this case.
</Callout>

## Scope

Cache affinity routing **does not apply to all models**. It is enabled only for specific models of the following protocols and providers:

| Protocol | Provider | Enabled models |
|------|------|---------|
| OpenAI Chat Completions | OpenAI | `gpt-4o`, `gpt-4o-mini`, `...` |
| OpenAI Responses | OpenAI | `gpt-4o`, `gpt-4o-mini`, `...` |
| Anthropic Messages | Anthropic | `claude-opus-4-6`, `claude-sonnet-4-6`, `...` |

<Callout type="warning" icon="exclamation-triangle">
  This list is updated as upstream providers adjust their caching policies. Models not on the list use default load balancing and are unaffected.
</Callout>

## Design trade-offs

Cache affinity routing is essentially a trade-off between **cache hit rate** and **traffic balance**:

- **Short TTL + request limit**: prevents traffic from concentrating on a single channel for long periods and avoids load skew
- **Unbind on error**: avoids continuing to route subsequent requests to a channel that has become unhealthy
- **Best effort**: affinity routing is an optimization, not a hard guarantee; a failure at any step silently falls back to the default logic

## Impact on users

- **No configuration required**; it takes effect automatically
- In coding assistant scenarios (Claude Code, Codex, etc.), the cache hit rate of continuous conversations improves significantly
- When the cache is hit, the upstream bills at the discounted price, and Poixe's charges decrease accordingly

## Recommendations for providers

We recommend deploying **accounts with sufficiently high rate limits** for model channels. Accounts with insufficient rate limits carry the following cascading risks:

- After a request completes, the system declines to establish affinity because the channel's rate is running short, wasting the caching opportunity of up to the next **100** consecutive requests
- From a data-plane perspective, between a low-rate account and a high-rate account, **the worst case can produce nearly a 100x difference in effective cached traffic**

<Callout type="warning" icon="exclamation-triangle">
  **Where the 100x difference comes from**: a single affinity binding can carry up to 100 requests. If insufficient rate prevents affinity from being established, all 100 of those requests fall back to default load balancing and cannot keep hitting the same channel's cache; an account with sufficient rate can fully use the 100-request window. The maximum gap in cache utilization between the two is therefore ~100x.
</Callout>
